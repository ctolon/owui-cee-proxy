# Branching, releases, and CI/CD

A short reference for how code moves from a feature branch to a
released artifact.

```
   feature/X ──► dev ──(PR + squash-merge)──► main ──► release.yaml
                                                       │
                                                       ├─► Docker Hub
                                                       ├─► GHCR (image)
                                                       ├─► GHCR (helm OCI)
                                                       ├─► CHANGELOG.md
                                                       └─► GitHub Release
                                                           (tag + notes)
```

## The two branches

| Branch | Purpose                                           | Direct push? |
|--------|---------------------------------------------------|--------------|
| `dev`  | Integration. CI runs on every push.               | yes          |
| `main` | Production. Every push triggers a release.        | NO — PR-only |

`dev` is the long-lived integration branch. Feature branches should
target `dev`. When a release-worthy bundle has accumulated on `dev`,
open a PR `dev → main`; merging it produces a release.

## PR title is the release contract

Squash-merge is the only allowed merge method on `main`. The
**squash-merge commit's title** is the conventional-commit message
that drives the next semantic version:

| PR title                                | Bump   | Example release |
|-----------------------------------------|--------|------------------|
| `feat: add MinerU adapter`              | minor  | `0.1.0` → `0.2.0` |
| `feat(engine): scoped feat`             | minor  | `0.1.0` → `0.2.0` |
| `fix: close DNS rebind window`          | patch  | `0.1.0` → `0.1.1` |
| `perf: lower spool threshold`           | patch  |                  |
| `refactor: rename …`                    | patch  |                  |
| `docs: explain mime routing`            | patch  |                  |
| `feat!: drop deprecated /v0/extract`    | major  | `0.9.0` → `1.0.0` |
| `chore: bump golangci`                  | none   | (no release)     |
| `test: …`, `build: …`, `ci: …`          | none   | (no release)     |

`pr-checks.yaml` enforces this using
[`amannn/action-semantic-pull-request`](https://github.com/amannn/action-semantic-pull-request)
— a malformed PR title fails the check and blocks merge.

A `BREAKING CHANGE:` paragraph in the PR body also forces a major bump
(via the `!` rule above).

## Release notes

Each release's GitHub Release notes are the **PR body verbatim**. The
release workflow looks the merged PR up by SHA, fetches its body, and
attaches it to the new release alongside the distribution table.

Independently, `CHANGELOG.md` is regenerated by
[`git-cliff`](https://git-cliff.org/) at release time using
`cliff.toml`. The file is committed back to `main` by the release
workflow with a `chore(release): vX.Y.Z [skip release]` message — the
`[skip release]` marker prevents an infinite release loop.

## Required GitHub repository secrets

Set these under **Settings → Secrets and variables → Actions**:

| Secret              | Purpose                                                      |
|---------------------|--------------------------------------------------------------|
| `DOCKERHUB_USERNAME`| Docker Hub username (e.g. `ctolon17`).                       |
| `DOCKERHUB_TOKEN`   | Docker Hub PAT with `read,write,delete` scopes for the repo. |
| `RELEASE_PAT`       | Fine-grained GitHub PAT with `contents: write` whose owner is in the ruleset's `bypass_actors` (typically the repo admin). Required for the release workflow's CHANGELOG.md commit-back to bypass the main protection rules. |

`GITHUB_TOKEN` is auto-provided. The release workflow uses it to:
- push image + helm chart to GHCR (`packages: write`)
- create the release + tag (`contents: write`)
- read PR body (`pull-requests: read`)

The branch protection ruleset must allow `github-actions[bot]` to
bypass it for the `chore(release): …` commit (otherwise the release
job cannot push CHANGELOG.md back to `main`).

## Branch protection ruleset

`.github/rulesets/main.json` is the source of truth for the `main`
branch ruleset. Apply it with:

```sh
# Initial create (also use to update — gh treats it as upsert by name)
gh api repos/ctolon/owui-cee-proxy/rulesets \
  --method POST \
  -H "Accept: application/vnd.github+json" \
  --input .github/rulesets/main.json

# List existing rulesets to confirm
gh api repos/ctolon/owui-cee-proxy/rulesets

# Update by ruleset id
RULESET_ID=$(gh api repos/ctolon/owui-cee-proxy/rulesets \
  --jq '.[]|select(.name=="main-branch-protection")|.id')
gh api repos/ctolon/owui-cee-proxy/rulesets/${RULESET_ID} \
  --method PUT \
  --input .github/rulesets/main.json
```

The ruleset enforces:

- `main` cannot be deleted, force-pushed, or have non-linear history
- Push to `main` requires a PR
- Merge method is restricted to **squash**
- All status checks must pass: `lint`, `test`, `build`,
  `helm-validate`, `manifests-validate`, `conventional commit title`,
  `gosec`, `govulncheck`, `trivy-fs`

`bypass_actors` lets repository admins push directly when needed
(emergency hotfix, release commit-back).

## ArtifactHub registration

Helm chart pushes go to `oci://ghcr.io/ctolon/charts/owui-cee-proxy`.
ArtifactHub indexes OCI registries; register the repo once at
https://artifacthub.io/control-panel → "Add repository":

- Kind: **Helm charts**
- Type: **OCI**
- URL: `oci://ghcr.io/ctolon/charts/owui-cee-proxy`

ArtifactHub re-indexes every ~30 minutes. Subsequent releases need
no manual step — the `org.opencontainers.image.source` annotation in
`Chart.yaml` keeps the GHCR package public on push.

## Skipping a release (docs-only PR)

A PR titled `chore: …`, `test: …`, `build: …`, `ci: …` produces no
semver bump. The release workflow will still run on the resulting
push to `main` but exit early with `::notice::no semver bump`.

To force-skip even when the title would bump (rare), add
`[skip release]` to the squash-merge commit message body.
